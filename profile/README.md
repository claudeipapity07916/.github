<p>代理配好了却上不去，多数人第一反应是「IP 不行，换一条」。但在换之前，有九成的故障能在十分钟内定位到具体环节：是本地没走代理，是认证没过，是 DNS 泄漏，还是出口到了但被平台拦。这篇用一棵故障树的方式把浏览器、手机、API 三种场景串起来，每个分支给出可执行的验证动作，让你在下单买新 IP 之前先确认问题真的在 IP 上。</p>

<h2>一、先画一棵树：连不上、连上慢、连上但被拦</h2>
<p>故障树的第一层只分三类，因为这三类的排查路径完全不同。连不上是链路或认证问题，连上慢是质量或拥塞问题，连上但被拦是出口身份或请求环境问题。搞错分支，后面的动作全是白费。</p>

<h3>连不上：从本机到出口逐跳</h3>
<p>先用 curl 指定代理访问一个稳定站点，看返回是超时、连接被拒还是 407。超时多半在链路，被拒多半端口不通，407 是认证没带上。三种结果直接把你送到不同的子树。</p>

<h3>连上慢：分清首字节慢还是传输慢</h3>
<p>用带时间分解的方式请求一次，看 DNS、连接、首字节、总耗时四段各占多少。首字节慢通常是出口到目标之间的问题，传输慢通常是带宽或线路拥塞。两者的处置完全不同。</p>

<h3>连上但被拦：先排除本地环境</h3>
<p>同一个出口，用干净的浏览器配置文件访问和在日常浏览器里访问，结果可能不同。差异来自 Cookie、扩展、时区语言设置。先确认这一点，再怀疑 IP。</p>

<h2>二、浏览器场景：三层配置，逐层验证</h2>
<p>浏览器这条链上有三层可能出错：系统级代理、浏览器启动参数、扩展自己的代理设置。三层同时开着会互相覆盖，出问题时很难判断哪层生效。</p>
<img src="/tp.png" alt="浏览器代理设置界面与命令行启动参数配置对照截图">
<p>建议只保留一层。日常办公用系统代理最省事；需要多环境隔离时用独立配置文件加启动参数，比如 --proxy-server 指定地址，配合 --user-data-dir 指定独立目录。两层都开的时候，实际生效的是后者，但前者仍会影响部分子进程。</p>

<h3>验证是否真的走了代理</h3>
<p>打开一个显示出口 IP 的页面，对比代理服务商后台看到的连接来源。两边一致说明生效；页面显示本地 IP 说明没走；页面打不开但后台有连接，说明是目标站点拒绝。</p>

<h3>扩展与新标签页的坑</h3>
<p>有些扩展会接管请求，绕过浏览器级代理；有些新标签页用了预渲染，走的是系统网络而不是配置的代理。排查时先禁用全部扩展，用命令行参数启动一个干净实例，问题消失就说明是扩展。</p>

<p>还有一处经常被误判：代理只改网络出口，不改本地时区。出口在美国而系统时区在东八区，页面上的一些时间显示和请求头会对不上。这不是 IP 的问题，但表现出来很像。把时区、语言、字体按出口地区调一致，能减少一类误判。</p>

<h2>三、手机场景：Wi-Fi 代理与热点共享的取舍</h2>
<p>手机上有三种常见做法：Wi-Fi 设置里填 HTTP 代理、装一个代理客户端、用电脑开热点共享。三者适用场景不同，故障表现也不同。</p>

<h3>Wi-Fi 代理：最轻，但只管 Wi-Fi</h3>
<p>在 Wi-Fi 高级设置里填主机和端口，只对当前这个 Wi-Fi 生效，切到蜂窝网络就失效。优点是无需装软件，缺点是部分应用不走系统代理，表现为「浏览器能开、App 打不开」。</p>

<h3>代理客户端：覆盖全，但要处理证书</h3>
<p>客户端通常用 VPN 接口接管全部流量，覆盖更完整。代价是需要处理 CA 证书，否则部分 HTTPS 请求会失败；iOS 上还要在「关于本机」里手动信任证书，这一步经常被漏掉，症状是「装好了但还是打不开」。</p>

<h3>热点共享：把手机当成终端</h3>
<p>用电脑开热点、在电脑上做代理，手机连热点。好处是配置集中在一处，坏处是手机的所有流量都绕了一圈，延迟增加，且热点本身的稳定性会成为新变量。</p>

<h2>四、API 场景：环境变量、SDK 与连接池</h2>
<p>脚本调用最常见的问题是「环境变量设了但没生效」。原因通常是 SDK 读取的变量名不同，或者进程启动时环境已经被父进程固定。</p>

<h3>先把变量设对</h3>
<p>通用约定是 HTTPS_PROXY 和 HTTP_PROXY，大小写都写一遍；NO_PROXY 里要排除本地地址，否则健康检查也会走代理。设完用 env | grep -i proxy 确认，再启动脚本，不要在一个已经跑着的 shell 里改完就以为生效。</p>

<h3>连接池会把并发悄悄放大</h3>
<p>默认连接池可能保留多条空闲连接，看起来只发了一个请求，代理侧看到五条。把池大小显式设成业务峰值，空闲超时设短一些，避免长连接一直占着出口。这一点在按并发计费时直接影响账单。</p>

<h3>超时与重试要成对设置</h3>
<p>连接超时 5 到 8 秒、读超时 90 到 120 秒比较适合长文本生成；重试只对 429、5xx 和连接错误生效，次数不超过三次，且带指数退避。设完用一次人为断网验证重试真的触发，别只看代码。</p>

<h2>五、按现象查表，别急着换 IP</h2>
<p>故障树的价值在于顺序。先确认「流量有没有真的出去」，再确认「出口是不是你以为的那条」，最后才判断「出口身份合不合适」。三步都过还不行，再考虑换线。</p>

<h3>三步确认法</h3>
<p>第一步看代理后台有没有对应时间的连接记录，没有说明流量没出去；第二步看记录里的出口 IP 是否与预期一致，不一致说明分流规则或池子轮换在起作用；第三步用同一出口在干净环境里重试一次，仍失败才归因到出口。</p>

<p>换线之后不要只看「能打开了」，把首字节时间、失败率、并发上限一并复测，否则可能只是把问题推后。复测结果记在同一个表格里，几次之后你就能看出哪类故障是线的问题、哪类是配置的问题。</p>

<h2>常见问答</h2>
<h3>浏览器能打开网页，但某个应用连不上，是什么原因？</h3>
<p>答：多半是该应用不走系统代理。系统级代理只影响读取系统设置的程序，很多客户端自己管理网络栈。改用接管全部流量的客户端模式，或在该应用内单独填写代理。</p>

<h3>手机装好客户端后所有 HTTPS 都失败，怎么查？</h3>
<p>答：先看 CA 证书是否被信任。iOS 需要在「关于本机」里手动开启完全信任，安卓在部分版本需要把证书装到系统区。证书未信任时，握手会直接失败，表现就是全部打不开。</p>

<h3>脚本里设了代理变量却没生效，问题在哪？</h3>
<p>答：三个常见原因：变量名大小写不匹配、进程继承了旧环境、SDK 使用自己的配置项而忽略环境变量。先 env | grep -i proxy 确认，再在代码里显式传参，最稳。</p>

<h3>同一个出口，浏览器正常但 API 返回 429，是 IP 的问题吗？</h3>
<p>答：不一定。429 通常与请求频率、并发数或账号额度有关，而不是出口身份。先看单位时间请求数和是否有多实例共用同一凭据，再考虑出口因素。</p>

<h2>合规提示</h2>
<p>本文的排查方法适用于自有账号与自有网络环境的日常运维。配置代理时应遵守所在网络的使用规定，不得用于未经授权访问他人系统或绕过平台安全机制。</p>
<p>使用代理服务前请确认服务商资质与线路来源合法，涉及跨境网络访问的应遵守所在地法律法规与平台服务条款。</p>
<p>文中参数为通用经验值，具体以你所使用的软件版本、SDK 文档与服务商说明为准。</p>
